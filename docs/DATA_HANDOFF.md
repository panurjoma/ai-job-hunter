# ChatGPT → GitHub → Python: event-driven inbox contract

**ChatGPT runs searches Tuesdays and Thursdays at 10:00 Europe/Madrid; the watcher runs Tuesdays and Thursdays at 16:00 Europe/Madrid.** It writes a validated JSON payload to the **default branch `main`** under `data/inbox/jobs_YYYY-MM-DD_HHMMSS.json`. This path-specific GitHub `push` event runs `.github/workflows/daily-job-search.yml`. No GitHub cron or workflow dispatch tool is required.

**Important:** the workflow must first be merged into `main` to be active for commits to `main`. ChatGPT must not commit inbox files to a separate branch expecting the main-only trigger to run. GitHub Actions runs under GitHub's identity; it cannot inherit ChatGPT's Gmail or LinkedIn OAuth credentials.

## Schema v1.1
See `data/inbox/example_jobs.json` for the canonical example. Each job must contain:
- Identity: `source`, `source_job_id` (if available), `company`, `title`, `url`, `application_url`, `source_url`.
- Timestamps: `posted_at` (if published), `observed_at`, `description_captured_at` in UTC ISO 8601.
- Remote: `remote_type`, `remote_evidence`, `eligible_countries`, `eligible_countries_evidence`. Unknown is **not** confirmed remote/country eligibility.
- Compensation: `salary` object with `min`, `max`, `currency`, `period`, `compensation_type`, `evidence`; use null for unknown, not fabricated values.
- Description: `description` as a faithful, readable full text extraction; `description_sections` with responsibilities, requirements, preferred, benefits arrays; `description_language`, `description_completeness` (`full`, `partial`, `unknown`), `description_source_url`, `description_truncated`, `description_notes`. Keep qualifications distinct from benefits, and preserve must-have vs nice-to-have wording.
- Context: `employment_type`, `seniority` where known.

## Description quality
Use the original company posting when possible. Preserve substantive responsibilities, stack, leadership scope, seniority, reporting line, remote location restrictions and compensation evidence. Strip navigation, cookies and marketing boilerplate. Never generate requirements or invent missing details. If only a snippet is accessible, set `description_completeness=partial` and `description_truncated=true`; mark eligibility unknown as needed. Retain source URLs for audit. Avoid sending HTML scripts, personal identifiers or tokens.

## Processing
`python -m job_hunter.cli --input data/inbox/jobs_YYYY-MM-DD_HHMMSS.json --output output/<batch> --pdf`

The pipeline deduplicates within a batch, validates eligibility, ranks jobs, and creates a separate role-prioritized HTML/PDF CV per shortlist entry. It does **not** auto-apply. The Action stores output as private workflow artifacts for 30 days; **artifacts are not commits to GitHub source history**. The ChatGPT task can send its Gmail report after it verifies the run/artifact state, but must not claim completion if it cannot inspect the result.

## Security and operational constraints
- This workflow uses `contents: write` to persist run receipts and generated CVs; the `push` path filter only triggers on new inbox JSON files, preventing recursive processing.
- Keep the repo private: inbox files include job descriptions and the master CV contains personal details.
- New JSON file names per run prevent silent overwrite. Commits to `main` can be restricted by branch protection; if protected, use a dedicated ingestion branch and update the workflow trigger accordingly.
- GitHub's `push` path filtering requires a workflow file present on the pushed branch. Test with a real commit after merging the PR.
- Existing score is deterministic keyword matching, not calibrated ML; review high-scoring jobs manually. Historical deduplication and semantic CV rewriting remain future improvements.

## Company maturity filter
ChatGPT should investigate the employer, not just the vacancy: founded year, years actively operating, whether a real product/service exists, credible customers or sustained operations, reputable parent company, and funding/runway evidence when public. Save the structured `company_profile` shown in the example payload with supporting evidence URLs. **Small size is not a rejection criterion.** Prefer companies with roughly 3+ years of demonstrable operations; a younger business may still qualify if it has unusually strong evidence of established commercial operations or backing. Explicitly unproven newly created companies should be rejected; unknown maturity goes to review, never invent evidence. The Python backend enforces the verified unproven exclusion and flags missing evidence for review.

## Permanent per-job CV storage
For every successful non-PR pipeline execution, generated files are committed to the **private** repository under `data/generated/<run_id>/attempt_<attempt>/<batch_name>/jobs/<job_id>/`. Each job folder contains `tailored_cv.pdf`, `tailored_cv.html`, `job.json`, and `tailoring_manifest.json`. Each batch also contains `report.json`, and each run attempt has a `manifest.json`. This is separate from temporary 30-day GitHub Actions artifacts. Because these are committed to Git, they persist in repository history until explicitly deleted/re-written. Only shortlisted jobs receive CVs; zero-match runs retain reports and a manifest but have no PDFs. The watcher should link to these paths and attach actual PDF bytes when its Gmail execution environment can access them; a GitHub URL alone is not a Gmail attachment. Do not claim attachment delivery unless verified.

## Employment quality and gig exclusions
Exclude Outlier.ai and similar task-based AI evaluation marketplaces, unassigned talent pools, pay-per-task contracts and staffing arrangements without an assured client project. Legitimate consulting roles with guaranteed employment or an assigned project remain eligible. Record engagement_model (direct_employment, assured_consulting_project, task_based_gig, ai_training_evaluator, talent_pool, contingent_project_matching, unassigned_contract or unknown), project_assured (true/false/null) and engagement_evidence. The backend rejects explicitly excluded models regardless of score; unknown contract assurance remains review.

## Official company logo handoff
ChatGPT should fetch a verified logo from the company's official website/brand kit and commit the PNG or safe static SVG into data/inbox/assets/<batch_id>/<job_id>.png (or .svg), BEFORE committing the corresponding job JSON. Set job.logo_path to that repo-relative asset and job.logo_source_url to its official source. Batch and job identifiers must use alphanumerics, underscores and dashes only. Assets must be under 150 KB; SVGs must have no scripts, styles, external references or embedded HTML. The renderer embeds the local image bytes as a self-contained base64 image in the top-right CV header (58px), requiring no network access during GitHub Actions. Missing/unverified logos should leave logo_path null; never fabricate a logo. The GitHub Actions JSON push must happen after logo files are on main.


## Technology-forward remote-negotiation candidates (Spain/Portugal only)
Fully remote jobs remain the first priority. Additionally, include **hybrid** vacancies and jobs whose remote policy is **unspecified** as a separate **review-only** category, regardless of industry (space, telecom, finance, healthcare, renewables and others). Require the role's office to be evidenced in Spain or Portugal (`hybrid_office_country`, `hybrid_location_evidence`) and a credible description **and official/source URL** showing the employer is technologically modern (`company_technology_evidence`, `company_technology_evidence_url`). Merely being in a particular industry does not prove technology-forward culture. Another actual fully remote vacancy at the same company (`company_other_remote_jobs: [{url, remote_type}]`) is **positive negotiating evidence, not a requirement**. If no other remote vacancy is found, explicitly say that remote feasibility is speculative. Reject explicitly onsite-only positions; do not assume a hybrid or unspecified vacancy can become remote. Display as **Potentially negotiable — not advertised fully remote**, separate from verified remote roles, with evidence and caveat. Salary floor, 60-point technical match, company maturity, and guaranteed employment requirements still apply. Do not misrepresent speculative opportunities as remote offers.

## Mandatory watcher email presentation (not optional)
For EVERY completed job-search run, the watcher must send a **rich HTML email**, not a one-paragraph plaintext summary. Each shortlisted vacancy must have its own visually separated row/card with:
1. **Company name and verified official logo** (image displayed inline at ~40–56 px, never only inside the attached CV). Use `logo_path` / `logo_source_url` from the committed inbox job and/or persisted `job.json`. Prefer a Gmail inline CID attachment if supported; otherwise a directly accessible verified official HTTPS logo URL in an HTML `<img>` tag. Never invent logos or use unverified third-party marks. If no verified logo exists, display a neutral company-name monogram and explicitly record `logo_missing`; do not silently omit the company identity. A logo embedded in a PDF does NOT appear automatically in an email.
2. **Job title hyperlinked to the actual job posting** using `application_url` when validated, else `url`; add a separate visible 'View position' link. Never replace position links with only a GitHub workflow URL.
3. **A concise, factual 2–3 sentence description** based on the source job description, including role scope, relevant stack/responsibilities and remote arrangement; do not invent requirements or compensation. Show score/100, work-mode classification, salary confidence, and any verification caveats. Explicitly label negotiable hybrid/unknown-work-mode candidates 'Potentially negotiable — not advertised fully remote'.
4. **Tailored CV PDF attached** with a readable matching company filename; verify attachment count against shortlisted count.

Before sending, assert: every shortlisted role has a nonempty source posting link and description; HTML contains one position hyperlink and one short description per shortlisted job; logo coverage is checked and missing logos are surfaced, not ignored; generated CV PDFs exist; the recipient and run ID match the receipt. On missing content, repair the data or report a blocked delivery instead of sending an incomplete digest. Check Gmail Sent for the run ID first and never resend an already delivered run. After a successful send, write `data/notifications/<run_id>_attempt_<attempt>.json` with Gmail ID, delivery status, attachment count, and `logo_present_count` / `logo_missing_companies`. If an earlier digest was already sent without these requirements, send a clearly marked **corrected report** once rather than silently overwriting its delivery receipt.

The search task must acquire and commit official logos BEFORE the inbox JSON commit. A missing official logo should be called out in the watcher and must not be misrepresented as an image. Search source coverage and role freshness must remain explicit.
